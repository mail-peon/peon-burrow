# 00 · 总览

> 一句话：**把「本地调试用的 TS 中继脚本」变成「用户装一次就不用管的常驻服务 + 图形安装器」。**

---

## 1. 它解决什么问题

`mail-peon` 扩展要收非 Gmail 邮箱（IMAP）的邮件，但 MV3 里**没有裸 TCP**，
所以必须有一个本机进程做 `WebSocket ↔ TCP/TLS` 的字节隧道（论证见
[`adr-0005-imap-needs-relay.md`](../../../mail-peon/ai-docs/decisions/adr-0005-imap-needs-relay.md)）。

现状是：用户得自己装 Node、拉仓库、敲 `pnpm relay`，还得**每次开机手动跑**。
对一个只想收验证码的普通用户，这条路的转化率约等于 0。

`relay-deployment.md § 1` 已经把这件事的结论钉死了：
**「零额外安装」与「不做公共中继」不可能同时成立**，于是选了第三条：
**装一次就再也不用管**（用户级自启 + 单二进制 + 安装器）。

本项目就是那第三条路的实现。

## 2. 目标（可验收）

| # | 目标 | 验收方式 |
| --- | --- | --- |
| G1 | **核心逻辑做成系统服务**，能开机自启、能被启停、崩了能自己回来 | `peon-hall` 上点「安装服务」→ 重启机器 → 扩展仍能收信 |
| G2 | **图形安装器**：显示服务安装状态 / 运行状态，提供 安装·卸载·启动·停止·开机自启 开关 | GUI 五个状态/五个操作与真实服务状态一致（含失败态） |
| G3 | 核心与界面**拆成两个项目**，各自独立发版 | 两条 CI：`core-v*` / `desktop-v*`，产物互不依赖（桌面端可单独发版，核心可单独升级） |
| G4 | 核心 CI **自动打包三平台** | Windows / macOS / Linux 各出可运行二进制，发到 GitHub Release |
| G5 | 桌面端 CI **自动打包三个桌面平台** | `.msi`+`.exe`(NSIS) / `.dmg` / `.AppImage`+`.deb` |
| G6 | 端口**可配置**，且默认值不撞车 | 默认端口经 IANA + Windows 动态/排除区间核过；配置文件可改；被占用时**不静默换端口**（扩展只认固定默认值）而是给出可执行的诊断，见 [`design/port-and-discovery.md`](./design/port-and-discovery.md) |
| G7 | 核心**自更新**（GitHub Releases 或镜像站）；桌面端**不检查更新** | 旧版本能自己升到新版本并重启服务；桌面端无任何联网检查逻辑 |

## 3. 非目标

| 非目标 | 理由 |
| --- | --- |
| 改扩展侧代码 | 协议冻结（[`adr-0002`](./decisions/adr-0002-rust-rewrite-scope.md)）。扩展需要改的只有「默认端口 + 文案」，在 mail-peon 仓库里做，属于 P6 联动项 |
| 公共中继服务 | 中继能看到邮箱明文凭据。托管 = 我们成为能看到所有人邮箱明文的那一方（`adr-0005` 的硬要求） |
| 中继解析邮件内容 | watch 只读 `LOGIN` / `SELECT` / `IDLE` 的响应行，拿不到主题与正文。**中继越笨，出问题时的破坏面越小** |
| 在桌面端里内嵌中继逻辑 | 桌面端是**安装器**，不是运行时。中继由服务跑；关掉 GUI 不影响收信 |
| 代码签名 / notarize（本期） | 成本项（OV/EV 证书、Apple Developer $99/年）。流程里预留，实施放 P5 之后，见 [`adr-0007`](./decisions/adr-0007-release-pipeline.md) |
| macOS/Linux 的深度适配（本期） | 先保证三平台能构建、能跑、能发版；LaunchAgent/systemd 的边角（如 `SMAppService`）逐步补 |

## 5. 术语表

| 术语 | 含义 |
| --- | --- |
| **中继 / relay** | 本仓库里的核心功能：一条 WebSocket 连接 ↔ 一条 TCP/TLS 连接的字节隧道 |
| **透传模式 / passthrough** | 扩展建立一次连接、发 IMAP 命令、收响应，用完就关（`fetch` 一轮同步用） |
| **watch 模式** | 扩展连上后第一帧发 `{"__watch":1,...}`，中继替它挂 `IDLE`，有新邮件推一行 JSON |
| **第一帧分流** | 同一个 WebSocket 端点靠第一帧是「二进制」还是「`__watch:1` 的文本 JSON」区分两种模式 |
| **控制面 / control plane** | 安装器 GUI ↔ 服务之间的本机管理通道（安装/卸载/启停/自启/状态），**与线上协议无关** |
| **发现文件 / port file** | 中继启动后写下的「我实际监听的端口」小文件，供 CLI / GUI / 排查使用 |
| **core tag / desktop tag** | 两个仓库各自的 `v<major>.<minor>.<patch>`（如 core 的 `v0.1.0`、desktop 的 `v0.1.0`）。core 的 tag 同时是桌面端钉 core 版本的锚点（[adr-0001](./decisions/adr-0001-two-repos.md)） |
| **sidecar** | 桌面端安装包内嵌的 core 二进制（Tauri 的 `externalBin`） |

## 6. 安全与隐私边界（必读）

这几条不是「注意事项」，是**产品的边界条件**：

1. **中继必然能看到明文。** TLS 是端点行为：要连 `imap.x.com:993` 就必须在中继里完成握手，
   握手之后的字节（含 `LOGIN` 里的授权码）就在中继进程里。**这不是缺陷，无法通过工程消除。**
2. **所以默认只绑 `127.0.0.1`。** 服务形态下**不提供**一键改成 `0.0.0.0` 的开关；
   要对外必须手改配置文件，并在启动日志里持续警告。
3. **绝不把凭据写进日志。** `RELAY_TRACE=1` 那套「打印原始字节」的能力在服务形态里
   **默认关闭且必须有显式二次确认**，日志落盘时也要打标记（见 [`logging-and-diagnostics.md`](./design/logging-and-diagnostics.md)）。
4. **自更新必须校验。** 一个能看到邮箱密码的常驻进程，不能从「任何拿到 URL 的人」那里拉二进制。
   最低要求：HTTPS + `SHA256SUMS` + 发布产物签名校验，见 [`update-flow.md`](./design/update-flow.md)。
5. **控制面只对本机开放。** GUI ↔ 服务的通道不允许从局域网访问；随机 token + 仅 loopback。

## 7. 成功判据（P6 结束时）

在一个**干净的 Windows 机器**上：

1. 下载 `peon-hall` 安装包 → 双击 → 点「安装服务」→ 出现一次 UAC（若选系统服务）或零 UAC（用户级）；
2. 打开扩展的账号页，**不填任何中继地址**，填 QQ 邮箱 + 授权码 → 能收到验证码推送；
3. 重启机器，**不做任何操作** → 仍能收到；
4. 拔掉扩展、只留服务 → 服务不崩、日志可读、`doctor` 能指出问题；
5. 服务升级：新版本 Release 发布后，旧服务在一个检查周期内自更新并恢复收信。

第 2 步的「不填任何中继地址」依赖 P6 联动（扩展默认端口改成新端口）。
在那之前，判据放宽为「填 `ws://127.0.0.1:<新端口>/` 能用」。
