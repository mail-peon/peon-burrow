# ADR-0002 · 重写范围：协议冻结、扩展不动、TS 版留作参照

- **状态**：已采纳
- **影响面**：本仓库的全部实现、与 `mail-peon` 的联动、验收方式
- **相关**：[`04-parity-node-to-rust.md`](../04-parity-node-to-rust.md)、[`wire-protocol.md`](../design/wire-protocol.md)

---

## 背景

现有实现是 `mail-peon/scripts/imap-relay.ts`（1901 行，单文件）。它的定位是**本地调试用**：

- 需要用户机器上有 Node + 仓库源码（`pnpm relay`）；
- 没有服务化、没有 GUI、没有自更新；
- 端口/白名单/证书校验都靠命令行与环境变量注入；
- 交互式控制台（`q` / `r`）只在 TTY 下可用。

但它已经**跑通了真实邮箱**（QQ 邮箱实测），并因此修掉了一批真机问题
（TLS 根本没握手、背压缺失、关闭帧超长崩进程、静默丢件…）。

原始计划（`mail-peon/ai-docs/decisions/relay-deployment.md § 5`）就是：
**第 4 步照抄成 Rust，第 5 步做安装器 + 服务注册 + 三平台打包**。本 ADR 把「照抄」的边界写清楚。

---

## 决策

### 1. 协议**冻结**，Rust 版是**同一个协议的第二个实现**

线上契约（URL 形态、第一帧分流、watch 的 JSON 字段、关闭码、`EXISTS` 语义）逐字见
[`wire-protocol.md`](../design/wire-protocol.md)。

- **不改协议**：包括字段名、默认值、错误语义、`tls !== '0'` 这种「看着奇怪但已发布」的判定；
- 唯一的**计划扩展**是版本协商（`protocol` 字段），且必须**向后兼容**：缺字段 = 版本 1，
  行为与 TS 版完全一致；
- 扩展侧代码**一行不改**（P6 只改默认端口与文案，那是产品决策不是协议变更）。

理由：扩展已经发布过、用户已经装过。协议变更意味着「用户必须同时升级扩展和中继」，
而这个项目的全部价值就是「一次安装、不用管」。

### 2.  **该不同的地方必须不同**（不是机械照抄）

TS 版有几处做法在服务形态下**是错的**，Rust 版必须偏离，且偏离要写进文档：

| 主题 | TS 版 | Rust 版 | 为什么 |
| --- | --- | --- | --- |
| 端口占用 | 交互提问 → `taskkill /F` 占用者 | 不杀、不换端口；先判断是不是自己的旧实例 | 服务没有 TTY；后台服务不该有杀任意进程的能力；扩展只认固定端口 |
| 崩溃兜底 | `uncaughtException` 吞掉继续跑 | 连接级隔离 + 服务层自动重启 | 吞异常 = 进程「假活着」 |
| 交互控制台 | 有 | 只有前台模式 | 服务态 stdin 是关闭的（TS 版自己都写了这个坑） |
| 配置 | CLI + ENV，模块级常量 | 再加 TOML 文件层（ENV 名兼容） | 服务不由用户手动启动；模块级常量导致一进程只能一个实例 |
| 日志 | stdout | 文件滚动 + 结构化事件 | 服务态没有终端 |

完整清单见 [`04-parity-node-to-rust.md § 4`](../04-parity-node-to-rust.md)。

### 3.  **不变的行为也不许悄悄变**

[`04-parity-node-to-rust.md § 3`](../04-parity-node-to-rust.md) 逐条列了 60+ 项行为，
分「必须一致 / 可以不同 / 应该不同」三档。其中「必须一致」的都是**用户或扩展能观察到**的，
或者**安全属性**（例如：策略检查必须同步、被拒连接不发字节、默认校验证书链、关闭原因 ≤120 字节）。

安全属性尤其不能只在功能测试里覆盖 —— 它在「写错」时功能测试**照样全绿**
（证书默认关掉时连接成功；策略检查延后时连接也成功）。所以有专门的断言，
见 parity § 6.1 的第 6 条与 § 6.2。

### 4. TS 版**不删**，冻结为「参照实现」

| 何时可以删 | 条件 |
| --- | --- |
| 现在 | ❌ 不能删。它是协议正确性的参照，且 `pnpm relay:test`（9 条断言）继续跑 |
| Rust 版通过 parity § 6 全部 20 条断言 | 🟡 可以开始讨论 |
| Rust 版在**真邮箱**（QQ 邮箱）上完整走完 `imap-testing.md § 4` 的验收清单 | ✅ 可以删 |
| 扩展侧默认端口切换到新端口并发布 | ✅ 必须删（否则两套实现都能占着默认端口，排查会混乱） |

冻结的含义：**不再给 TS 版加功能、不再为它做优化**。
只允许「修协议正确性 bug」，且该修复必须**同时**进 Rust 版（否则两边行为分叉）。

## 后果

### 好的

- Rust 版有**可执行的验收标准**（60+ 行为条目 + 20 条断言），不是「凭感觉重写」；
- 出问题时可以把两个实现对着跑（同一个 mock IMAP 服务器、同一个 echo 服务器），
  「Rust 版行为和 TS 版不一致」是一个**可测**的判据；
- 扩展不用动，用户不用同时升级两端。

### 代价（如实记录）

| 代价 | 说明 |
| --- | --- |
| 60+ 条行为要逐条对齐 | 这是本项目最大的一块工作量，也是最大的一块价值；parity 文档就是为它存在的 |
| 一段时间的双实现维护 | 用「冻结 TS 版功能」+「协议 bug 双改」限制在可控范围 |
| 有些 TS 行为看起来「不优雅」，但仍要保留 | 例：`tls !== '0'`（而不是 `tls === '1'`）、问候语靠「第一条 `* `」判定。**它们都是踩坑换来的**，见 parity 文档里对应行的理由 |

### 明确不做的

| 不做 | 理由 |
| --- | --- |
| 借重写机会「顺便把协议改干净」 | 会同时要求用户升级扩展 —— 与产品目标冲突 |
| 让 Rust 版继续支持 `node ../imap-relay.ts` 那种运行方式 | 那是调试路径，`run --foreground` 已经覆盖 |
| 把 IMAP 协议栈也搬进 Rust | 中继是**字节隧道**，不解析 IMAP（watch 除外，它只读响应行）。协议栈在扩展里 |
