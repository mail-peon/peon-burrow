# S14 真机验收清单 · [S14-release-checklist]

> **目的**：首发 `v0.1.0` 之前，逐条验证「在普通用户的真实机器上确实能跑起来」。
> 任何一条失败 = 不能发版 —— 不接受「理论上对」/「开发机过」/「CI 过」。
>
> **范围**：三平台（Windows / macOS / Linux）× 三种安装形态（用户级 / 系统级 / 前台），
> 完整跑一遍「装 → 配置 → 收信 → 重启 → 崩溃恢复 → 自更新 → 卸载」全流程。

---

## 0. 环境前提

- [ ] **干净 Windows 10/11**（或 macOS 13+ / Ubuntu 22.04+），**没有** Node / Rust / 任何中继程序
- [ ] **真实可用的 IMAP 邮箱**：QQ 邮箱（推荐）、Outlook、网易 126/163、Gmail 任意之一
- [ ] **真实可用的 AI Key**：OpenAI / DeepSeek / Anthropic 至少一个
- [ ] **真机有至少 1 小时的连续开机时间**（用来验重启 / 崩溃恢复）
- [ ] **安装包来自 CI 产物**（不是 `cargo run` 自己编译的）

> 拒绝把「开发者本地跑过」算作验收。CI 产物是给用户的、对的形态——它必须能装、能跑。

---

## 1. 安装（用户级，默认路径）

### 1.1 桌面端装好

- [ ] **Windows**：`peon-hall-v0.1.0-x64-setup.exe` 双击 → 不弹 SmartScreen / 弹了能「仍要运行」 → 安装完成
- [ ] **macOS**：`.dmg` 拖进 Applications → 双击启动（首次可能弹 Gatekeeper，确认即可）
- [ ] **Linux**：`peon-hall-v0.1.0-x86_64.AppImage` 加可执行权限 → 双击启动

### 1.2 首次启动

- [ ] 状态卡片显示「未安装」
- [ ] 顶部无黄条 / 红条
- [ ] 控制面没有「连不上」类提示
- [ ] 「诊断」按钮可见

---

## 2. 中继服务装好

### 2.1 点【安装服务】

- [ ] **Windows 用户级**：不弹 UAC（即 0 次管理员授权）
- [ ] **Windows 系统级**：弹一次 UAC，取消后界面显示「已取消」（**不是**错误）
- [ ] macOS / Linux 用户级：跑安装的子命令无错误
- [ ] macOS / Linux 系统级：弹一次授权框（pkexec / sudo），同上取消可回退

### 2.2 装完应该自动启动

- [ ] 状态卡片 3 秒内变「正在运行 · 端口 41316 · v0.1.0」
- [ ] 【停止】按钮可用，其余主次按钮不存在
- [ ] 「扩展地址」行显示 `ws://127.0.0.1:41316/`（来源：「运行中的中继」）

### 2.3 重启机器

- [ ] 不需要任何操作，重启后扩展照常收信
- [ ] 桌面端打开 → 状态卡片仍显示「正在运行」
- [ ] 服务管理器里能看到 `peon-burrow` 注册项（`schtasks` / `launchctl list` / `systemctl --user status`）

---

## 3. 扩展装好 + 收信

> **真实装好 / 加载扩展** + 与 puppeon-hall 的衔接（本文档展开 5.7）

- [ ] 扩展在 Chrome / Firefox 装好
- [ ] 「设置 · 账号」配一个 IMAP 账号（推荐 QQ：imap.qq.com:993）
- [ ] 「设置 · AI 配置」填一个 AI Key，点「测试连通」通绿
- [ ] 「立即同步增量」按钮按一下 → 扩展收到验证码 toast，**剪贴板自动有验证码**
- [ ] **重启浏览器 + 不重启操作系统** → 扩展仍能持续收信（验证 SW 唤醒）
- [ ] **重启操作系统** → 启动扩展，仍能持续收信（验证服务常驻）

---

## 4. AI 多 Provider × 真邮箱

每个 Provider 跑一遍验证码邮件（**至少有 QQ 验证码邮件**才方便验）：

- [ ] **OpenAI**：扣费、返回 JSON、UI 显示「正在运行 / 端口 / 监听数」
- [ ] **DeepSeek**：默认关闭思考模式（开了会导致输出为空，已知问题）→ UI 正确
- [ ] **Anthropic**：长邮件理解力好，验证码抽取要能跑出来
- [ ] **Custom（OpenAI 兼容）**：至少一个镜像站配通

### 4.1 验证码邮件

- [ ] 主题/正文含「验证码」/「code」/「OTP」 → 极简模式自动入库；完整模式摘要 + 验证码
- [ ] 验证码显示「倒计时」（AI 读出 `validForSeconds` 的场景）
- [ ] 倒计时到 0 + 30 秒后，邮件被自动移到回收站
- [ ] 回收站可恢复，「彻底删除」与「清空回收站」不可撤销

### 4.2 长邮件

- [ ] AI 摘要 + 主题 + 发件人 + snippet 都对得上
- [ ] 输入超 token 限制时**不**截断整个邮件——按「先看 subject / from」规则
- [ ] 解析失败不卡流程（zod 异常不影响下一封）

---

## 5. 自更新（首发风险最高的一段）

### 5.1 准备

- [ ] 已经在 `beta` 渠道发布过一次 `v0.1.0-rc.1`，清单可访问（GitHub + 至少一个镜像）
- [ ] `latest.json` 的 `signature` 字段缺省（v0.1.0 不签），release notes **明确写**这是无签名升级通道

### 5.2 升级路径

- [ ] 在「诊断」面板点「检查更新」→ 提示已是最新
- [ ] 手动 `burrow update check --force` → 提示已是最新
- [ ] 临时改 `core-version.txt` 为 `v0.1.1-rc.1` → 重启中继 → 自动下载新二进制
- [ ] 下载中：状态卡片显示「正在更新并重启中继…」
- [ ] 完成后：状态卡片显示新版本号；扩展自动重连（验证 watch 失败 → 重连逻辑）

### 5.3 失败路径

- [ ] `sha256` 错的清单 → 拒收（验证 fail closed）
- [ ] 镜像站 404 → 切换到下一个镜像；全部失败时报错信息说明白了
- [ ] 磁盘满 → 拒绝替换、保留原二进制
- [ ] staging 二进制冒烟失败（`version --json` 不返回）→ 拒绝替换

### 5.4 服务管理器拉起新进程

- [ ] Windows 服务模式下，非零退出码被「失败重启」拉起
- [ ] macOS launchd / Linux systemd --user 下同

---

## 6. 崩溃恢复

- [ ] 在 `burrow run` 跑着的时候，`kill -9 <pid>`
- [ ] 服务管理器检测到崩溃 → 自动重启（最多 30 秒）
- [ ] 扩展侧 watch 自动重连（不应要手动干预）
- [ ] 控制面状态从「已安装未运行」→「正在运行」在 30 秒内

### 6.1 扩展不停日志

- [ ] 在扩展 background 跑的时候，杀掉 Chrome
- [ ] 重新打开 Chrome → watch 通道 30 秒内重连

---

## 7. 卸载

- [ ] 点【卸载服务】→ 服务停止 + 注册项消失
- [ ] 配置与日志按「保留」选项保留
- [ ] 控制面发现文件 `/run/peon-burrow/control.json` 等被清掉（或保留按选项）
- [ ] 桌面端显示「未安装」
- [ ] 桌面端自身可独立卸载（不依赖中继）

---

## 8. 跨平台 smoke（任一平台跑过即可）

- [ ] 三平台都装一遍
- [ ] 三平台都能跑通 1.1 → 7
- [ ] 三平台的产物都来自 `assets.yaml` 的 CI（**不是**开发者本地编译）

---

## 9. 拒绝发版条件（任一条即拒发）

- [ ] **任一平台** §2 / §3 / §5 任意一条失败
- [ ] **任一 AI Provider** §4 失败
- [ ] **任一崩溃路径** §6 让服务起不来
- [ ] CI 产物与本清单步骤无法复现（即步骤是用本地 `cargo run` 蒙混过的）
